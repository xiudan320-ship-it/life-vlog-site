## 1. 目标与当前基线

本轮不重做视觉风格，只解决已确认的三类体验问题：

1. 手机端切换“日记 / 心愿 / 周末 / 衣柜”时，会继承或截断上一页滚动位置，进入新页面后落在中间区域。
2. 登录与注册表单同时展开，信息层级不清楚；输入框缺少可见标签，密码也无法查看。
3. 手机端部分文字和点击区域偏小，首页大图副标题在图片上的实际对比度不足。

产品定位已经确认：手机端按 App/PWA 式固定视口使用，保留禁止双指缩放的现有策略。可读性通过字号、对比度、触控尺寸以及小屏/横屏适配解决，不开放页面缩放。

当前线上基线：

- 正式站：`https://life-vlog-site.pages.dev`
- 最近一次预览：`https://87e78d2c.life-vlog-site.pages.dev`
- 当前 Service Worker 缓存版本：`life-vlog-site-20260827-006-pwa`
- 当前入口版本：`app.js?v=20260827-002`
- 最近完整测试基线：17 项单元测试及静态、结构、浏览器回归测试通过

已观察到的关键问题：

- 手机端在日记页滚动到较深位置后首次切换心愿页，页面可能停在约 `scrollY=400`；再切到周末页可能停在约 `scrollY=286`，而不是页首。
- 页面切换后键盘焦点仍停在原导航按钮上，新页面没有明确的当前页语义。
- 手机端主导航按钮约 36px 高，主题按钮约 40px，“忘记密码”区域约 23px 高。
- 日记作者、日期、工具说明等可见信息大量使用 9–11px 字号。
- 首页大图副标题叠加在图片上时，估算对比度约为 3.25:1；小号正文目标应达到至少 4.5:1。

## 4. 文件职责与实现边界

预计涉及的主要文件：

- `modules/app-navigation-controller.js`：页面切换、分页面滚动位置、焦点移动、当前页语义。
- `modules/app-event-bindings.js`：只保留事件绑定和对导航控制器的调用，不在这里复制导航状态逻辑。
- `modules/auth-controller.js`：登录/注册模式、密码显隐、提交行为和错误状态。
- `modules/auth-view.js`：仅当账户区域的 DOM 状态切换明显增长时新增；负责渲染/显隐和无障碍属性，不承载认证业务逻辑。
- `index.html`：账户区语义结构、可见标签和必要的静态无障碍属性；viewport 保持现状。
- `styles/redesign-foundation.css`：现有全局/页面级视觉规则的定向调整。
- `styles/mobile-page-shell.css`：仅放真正属于移动页面壳层的规则，避免与基础样式重复定义。
- `tests/`：增加导航、账户、响应式和静态契约回归。
- `app.js`、`service-worker.js`、`index.html`：只做模块装配和资源版本更新，不在入口文件新增功能逻辑。

如果实际文件组织与以上描述不完全一致，优先沿用现有模块边界；不要为了严格匹配文件名而制造重复职责。

## 5. 分阶段实施方案

### 阶段一：修复顶级页面导航

实现位置以 `modules/app-navigation-controller.js` 为主。

#### 行为要求

1. 切换页面前，记录当前顶级页面的 `window.scrollY`。
2. 每个顶级页面拥有独立滚动位置：`diary`、`wishlist`、`weekend`、`wardrobe` 互不覆盖。
3. 某页面第一次进入时滚动到 `0`。
4. 返回已访问页面时恢复其上次位置，并把目标值限制在当前页面可滚动范围内。
5. 恢复滚动必须使用即时滚动，不使用 smooth scrolling。
6. 先完成页面显隐和必要渲染，再在下一渲染帧恢复滚动，避免目标页面高度尚未稳定时恢复失败。只使用满足需求的最少帧数，不引入定时器链。
7. 切换完成后，将焦点移到新页面的主标题；标题可使用 `tabindex="-1"`，调用 `focus({ preventScroll: true })`，避免焦点操作破坏已恢复的位置。
8. 当前导航项设置 `aria-current="page"`，其余顶级导航项必须移除该属性，任何时刻只能有一个。
9. 快捷入口或菜谱入口若本来就需要打开页面后定位到编辑器/指定内容，应保留该明确行为；不能被通用滚动恢复逻辑覆盖。
10. 品牌 Logo 返回首页并滚动页首的既有行为保持不变。

#### 验收标准

- 日记页滚动到 `1800` 后，首次进入心愿页时 `scrollY=0`。
- 在心愿页滚动后切走再返回，恢复到合理误差范围内的原位置。
- 周末页、衣柜页重复以上逻辑均成立。
- 页面内容变短时，不产生超出最大范围的空白滚动位置。
- 键盘用户切换页面后，焦点位于新页面标题，继续按 Tab 能进入该页的第一个可交互元素。
- 顶级导航只有一个 `aria-current="page"`。

### 阶段二：重构账户区域的信息层级

账户区域采用单一模式渐进披露，不再同时展示完整登录和注册流程。

#### 登录模式（默认）

- 显示用户名、密码、登录主按钮。
- 显示“注册账户”入口，用于切换到注册模式。
- 邀请码输入框和注册提交按钮不显示，也不参与校验。

#### 注册模式

- 显示用户名、密码、邀请码和注册主按钮。
- 提供清晰的“返回登录”入口。
- 模式切换时保留用户已输入的用户名和密码；邀请码只参与注册提交。

#### 表单与无障碍要求

1. 每个输入框都有可见 `<label>`，不能仅依赖 placeholder。
2. 用户名使用 `autocomplete="username"`。
3. 登录密码使用 `autocomplete="current-password"`；若注册密码使用同一输入框并动态切换模式，应按模式切换为合适的 `new-password`，不要同时保留冲突属性。
4. 邀请码使用 `autocomplete="off"`。
5. 密码框提供原生 `<button type="button">` 显隐控制，并同步可访问名称和按下状态，例如 `aria-pressed`。图标使用项目已有 SVG 语言，不新增 emoji/字符图标。
6. “忘记密码”的实际点击区域至少 `44 × 44px`，视觉文字可以保持紧凑。
7. 字段错误与对应输入框通过 `aria-describedby` 关联；无效字段设置 `aria-invalid="true"`，修正后移除。
8. Toast 或状态提示不得无故抢走输入焦点。
9. 登录、注册、忘记密码的既有业务调用和返回信息保持不变；本轮只调整交互层级和可访问性。

#### 验收标准

- 初始只看到登录流程，邀请码默认隐藏。
- 点击注册入口后邀请码和注册主操作出现，返回登录后再次隐藏。
- 模式来回切换不清空用户名和密码。
- 密码显隐按钮不会提交表单，状态和可访问名称正确变化。
- 使用键盘可完成模式切换、输入、密码显隐和提交。
- 浏览器密码管理器可正确识别用户名与密码字段。

### 阶段三：定向改善手机端可读性和触控

只修改确有问题的移动端选择器，不进行全局字号替换。

#### 必须调整

- 顶部主导航按钮最小高度提升到 `44px`。
- 主题、设置、通知等主要图标按钮的触控区域至少 `44 × 44px`。
- “忘记密码”触控区域至少 `44px` 高。
- 日记日期、作者、工具副标题等承载实际信息的移动端文字不小于 `12px`；优先使用 `12–13px` 并结合行高验证。
- 首页大图副标题在手机端提升到约 `14px`，同时通过增强局部遮罩、文字颜色/不透明度或其他现有设计语言内的方式，使最终合成对比度达到至少 `4.5:1`。
- 正文仍按正常可读字号处理，不要借本轮任务缩小正文。
- 保持深色、浅色主题的 token 体系，不写只对单一主题有效的硬编码补丁。

#### 可以保留

- 纯装饰性 overline、标签或非必要的微型文字可保持较小，但必须确认它不承载用户完成任务所必需的信息。

#### 验收标准

- `390 × 844` 下主导航、主题/设置/通知按钮和忘记密码均达到规定触控尺寸。
- 调整后不造成导航拥挤、换行错位、卡片高度异常或横向溢出。
- 首页副标题在浅色/深色主题和真实背景图叠加状态下均清晰可读。
- `1440 × 900` 桌面端布局与现有宽度、密度基本不变。

## 9. 风险与边界情况

- 页面异步渲染可能改变页面高度。滚动恢复要放在可预测的渲染完成点，不要用随意延迟的 `setTimeout` 掩盖竞态。
- 标题聚焦会触发浏览器自动滚动，因此必须使用 `preventScroll`，并验证 Safari/移动端退化行为不会让页面跳动。
- 系统大字体会增加固定头部和表单所需空间，要确认焦点目标没有被头部遮挡；必要时使用现有布局变量或 `scroll-margin`，不要写页面专用魔法数字。
- 登录/注册共用字段时，要避免隐藏字段仍然被浏览器原生校验拦截。
- 密码显隐不能重建输入框，否则可能丢失光标位置、自动填充或已输入内容。
- 提升触控区域时优先扩大按钮盒子或伪元素命中范围，不要单纯放大图标破坏视觉比例。
- 首页副标题对比度必须按图片叠加后的真实效果判断，不能只比较 CSS 中两个孤立颜色值。
- 修改 Service Worker 时要确认旧缓存可被正常淘汰，但不要新增兼容层或迁移逻辑。
