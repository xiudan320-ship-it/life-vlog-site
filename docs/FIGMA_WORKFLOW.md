# Figma UI 工作流与首页试点规划

本文件用于后续 Figma 设计、设计稿实现和任务交接。普通局部 UI 修复无需读取；开始 Figma 任务时只读当前阶段，进入下一阶段再补充。

项目规则见 [AGENTS.md](../AGENTS.md)，现有视觉基准见 [DESIGN.md](../DESIGN.md)。文档读取与同步由 [README.md](README.md) 统一决定；本文件不复制发布清单或完整设计系统。

## 1. 选择任务路径

| 任务 | 执行方式 | 本文相关章节 |
| --- | --- | --- |
| 文案、间距、局部溢出、焦点或按钮反馈修复 | 定位源码后直接修复，做受影响范围的验证 | 无需读取本文 |
| 整页改版、新页面、导航结构调整或多种视觉方案比较 | 优先在 Figma 做可编辑方案，再按授权范围实现 | 2–5，进入实现后读 6–7 |
| 用户明确要求使用 Figma，包括局部修改 | 在指定文件和节点中完成任务 | 2–5 |
| 用户提供确定的 Figma 设计要求实现 | 读取节点设计上下文，直接进入代码实现 | 2、3、6–7 |
| 只调整开发规则或写规划 | 更新文档与链接，检查一致性和 diff | 无需创建 Figma 文件或运行网站测试 |

Figma 负责可视化设计与评审，项目代码负责运行行为；包含代码实现时由浏览器完成最终验收，纯设计交付验收实际 Figma 设计产物。`ui-ux-pro-max` 只在存在具体设计疑问时查询相应内容，不运行例行全站搜索，也不重新生成整套设计系统。

## 2. 范围、设计依据和授权

开始前用简短任务说明确定：改哪个页面或组件、要解决的问题、交付设计稿还是同时实现、需要展示的设备和状态。可以从已有指令推断的内容直接沿用，不重复询问。

- 沿用现有浅色/深色绿色系外观、黑猫原图与 Logo；资产保护和布局约束以 DESIGN 为准。除用户明确调整外，保留现有导航行为、桌面日记四列和今日心情侧栏规则。
- CSS 实际变量、字体及最终计算样式是还原当前页面的依据。`MASTER.md` 中标为参考的 token 不能直接当作当前代码契约。
- 已确认的 Figma 节点描述本次设计目标；现有源码和运行页面描述当前实现。二者不一致时记录差异，依据本次需求修改，不能用旧截图掩盖已授权的新设计。
- Figma 自动生成内容和通用技能建议须适配用户要求及项目规则。影响范围以任务为边界，不因创建组件而扩展为整站改版。
- 只要求设计稿时，完成可审阅方案后交付；已授权设计并实现、或已选定方案时，继续实现和验证。存在实质性方案取舍才展示具体方案请用户决定，不把每个阶段设成确认关卡。
- 发布是独立范围，沿用会话中已有的发布授权及仓库发布规则；设计稿通过不等于网站已上线。

## 3. 接入与技能选择

### 首次使用或目标文件改变时

1. 确认当前会话有实际可调用的 Figma 工具，并以最小范围读取确认目标文件访问能力。安装状态、技能目录存在都不能代替一次成功的工具操作。
2. 优先复用用户指定或此前记录的项目文件；文件内先查目标页面和节点，避免重复建稿。
3. 需要新文件时按 `figma-create-new-file` 技能选择账户/计划，创建 Design 文件。多账户或团队归属无法从已有上下文确定时，才请用户选择。
4. 把工具返回的文件链接及相关节点链接记入第 9 节。链接和 ID 必须来自实际结果，不填写猜测值。
5. 如果工具、权限或必要节点不可用，报告具体未完成阶段，并继续可独立进行的源码定位、布局问题整理或文档工作；不把本地截图当成已完成的 Figma 设计。

不要把本机插件缓存路径、版本号、账户密钥或会话凭据写成项目配置。后续任务从当次技能目录定位所需技能，工具参数以当次工具说明为准。

### 按实际操作加载技能

| 操作 | 需要读取的技能 |
| --- | --- |
| 创建新的 Figma 文件 | `figma-create-new-file`，在每次 `create_new_file` 前加载 |
| 从页面、代码或说明创建/更新完整视图 | `figma-generate-design`；调用 `use_figma` 前同时加载 `figma-use` |
| 创建可复用组件、变体或变量系统 | `figma-generate-library` + `figma-use`，范围只覆盖本次需要的组件 |
| 在 Figma 内执行其他脚本读取或编辑 | `figma-use`，按当前操作读取相关说明 |
| 把 Figma 节点实现为项目代码 | `figma-design-to-code`，写代码前通过 `get_design_context` 获取目标节点上下文 |

只加载实际使用的技能，不预读整个 Figma 插件。首次试点不要求引入 Code Connect、发布团队组件库、安装前端框架或增加新的构建步骤；已有映射和组件库则优先复用。

同一 Figma 文件的写入操作，以及依赖前一步写入结果的读取或导入，按顺序执行；当前工具支持时，彼此独立的只读发现才可以并行。

## 4. 从运行页面建立设计基准

1. 按页面名称、文案或模块定位直接相关源码，读取对应设计规范；从实际 CSS 提取字体、颜色、间距、圆角和断点。
2. 需要还原运行页面时，使用现有本地运行方式展示页面。需要登录态或列表数据时，复用 [内存 API fixture](../tests/fixtures/cloudflare-api-fixture.mjs) 和现有浏览器测试的注入方式；设计捕获使用合成记录与测试图片，品牌资产按 DESIGN 使用，不把私人日记或照片上传到 Figma。
3. 只有运行页面是本次设计依据时，才捕获代表性手机与桌面页面，并记录尺寸、主题、fixture 状态和基准提交。截图用于对照；最终设计中的布局、文字和控件应可编辑。
4. 页面含图片且确实需要还原运行页面时，遵循 `figma-generate-design` 的捕获与组件构建流程，使用同一目标文件；已有图片填充或可用 `upload_assets` 提供素材时直接复用/上传，不因页面含图片而强制捕获。按技能验证图片完整性和可编辑性，不留空占位。
5. 保留有用的基准对照及节点链接。只有确认图片已转移、可编辑设计完整后，才清理本次工具产生的临时捕获节点；不删除用户已有设计。

复用现有 fixture，只有当前页面缺少必要状态时才补充它；不为设计建立第二套模拟后端、真实测试账户或长期后台服务。

## 5. 在 Figma 中完成可实现的方案

### 文件组织

首次试点只需要基准对照、首页方案、必要的局部组件三个区域，可使用已有页面内的 Section。后续页面在实际启动时添加，不预建全站空目录或每次复制整份文件。

- 命名体现页面、尺寸、主题和状态，例如 `首页 / 390 / 浅色 / 默认`。
- 检查本次需要的已有组件映射、文件内实例和可用库，再按相关技能补齐缺少的组件。以本项目样式为准，不为使用某个库改变视觉语言。
- 使用 Auto Layout、合理的伸缩约束与真实文字；只把本次重复使用的元素提取为组件。共享变量映射到现有 CSS 语义变量，不另建平行命名体系。
- 设计同时说明内容增长后的行为：长标题、缺失图片、较多标签、不同卡片高度；列表和布局不能只在一张静态样例中成立。
- 为本次涉及的控件标注选中、焦点、禁用、加载、空、错误等必要状态及交互结果。原型用于表达关键路径，无需模拟全部业务系统。
- 先完成一个有依据的推荐方案；仅在真实存在取舍时增加备选，不默认制作多个主题或三套方案。

### 设计阶段交付

提供目标节点链接、手机/桌面对照、主要变化说明和仍需决定的取舍。记录需要改动的现有组件及代码位置，注明设计中哪些交互仍待浏览器验证。只有设计任务时，到此交付；已授权实现时继续下一阶段。

## 6. 将设计落实到当前项目

1. 对已确定的目标节点调用 `get_design_context`，按节点拆分过大的读取。优先复用当前任务上下文、交接记录或文件映射中已经明确的 `fileKey`/`nodeId`；缺少且无法唯一定位时才询问用户，不能编造 ID；无法读取时说明缺口。
2. 将工具参考代码转换为项目现有的 HTML、CSS、原生 JavaScript 和模块组织。即使工具返回 React/Tailwind，也不因此安装它们或替换当前构建链。
3. 优先调整已有视图和组件样式。新增职责放入 `modules/`，`app.js` 继续只负责装配；没有业务需求时保留已有数据契约、缓存和事件行为。
4. 使用现有语义 CSS 变量及布局方案，替换本次已过时的规则，避免在样式末尾不断叠加覆盖层。不要将画布绝对坐标照搬成无法响应内容的页面。
5. 优先复用项目现有图片和图标；新增设计资产使用准确导出，并落入项目资产流程。交付代码不能依赖会过期的 Figma 临时链接；动态照片继续使用项目数据源。
6. 以相同尺寸、主题和 fixture 比较运行页面与目标设计，修复影响层级、间距、字体、媒体比例或点击区域的偏差。浏览器行为与设计目标一起验收。
7. 若设计涉及全局规范变化，按文档路由同步设计系统；仅任务局部变化不重写全局规范。回填最终节点、代码提交和已接受的差异。

## 7. 验收与交接

视觉和交互验收遵循 [DESIGN.md 的检查范围](../DESIGN.md#按需阅读与验收)，测试风险分级遵循 [CHANGE_WORKFLOW.md](CHANGE_WORKFLOW.md#4-测试范围)。不因使用 Figma 就扩大为全站测试。

| 本次变化 | 对应验证入口 |
| --- | --- |
| 仅设计稿 | 查看实际 Figma 节点及导出对照，检查可编辑性、主题、状态与约束；不报告网站测试通过 |
| 局部源码或样式 | 受影响页面的浏览器检查；按范围使用 `pnpm run check`、`pnpm run test:static`、`pnpm run test:structure` |
| 控件行为、导航或共享布局 | 对应模块测试与浏览器回归；现有入口为 `pnpm run test:browser`，按实际风险选择相关脚本 |
| 键盘、语义、对比度或共享组件变化 | 浏览器人工交互检查及现有 `pnpm run test:a11y`；运行前按脚本说明准备本地 URL |
| 构建入口、资产加载或性能变化 | `pnpm run build`、`pnpm run test:build` 及相关启动/性能回归 |
| 获准发布 | 读取并执行 [发布清单](release-checklist.md)，不在本文维护第二套发布命令 |

命令来源是 [package.json](../package.json)；执行前检查相关脚本当前的服务和构建前提。包含代码实现的首次首页试点至少覆盖导航、搜索/筛选、卡片打开关闭、今日心情入口及设计中受影响的状态；纯设计稿只验收实际 Figma 节点的可编辑性、状态和约束，不为此强制启动网站。图片和 API 数据继续使用确定性 fixture。

交付时简要列出：Figma 文件与目标节点、实际修改、验证命令及结果、尚未验证的内容和必要差异。代码或文档修改均运行 `git diff --check`；纯文档更新不部署。
