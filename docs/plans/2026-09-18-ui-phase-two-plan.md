## 3. M：日记图片横向排列

### 3.1 已确定形式与修改边界

本轮按用户授权确定为“同一篇日记里的多张图片横向排列，可左右浏览”：卡片内轨道显示两张预览，后续图片用原生横向滚动与 snap 访问，末尾提供“查看全部 N 张”并进入既有详情。整页仍禁止横向滚动，不同时实现左图右文等第二种方案。

默认目标是首页日记卡片的多图区域，不将整条日记列表改为横向滚动。保留桌面四列、手机现有单列/双列设置、时间排序、标题正文、上一轮的收藏/更多菜单。手机详情已有横向缩略图和切图逻辑，先复用对应图片索引，不重复建一套详情查看器。

当前多图的正方形拼贴换为一行横向预览轨道；多图增加时不再向下增加图片行。单张图片不需要横向滑动，沿用当前稳定比例与完整查看入口。此范围是规划的默认解释，不代表用户已经确认“不改卡片结构”。

### 3.2 推荐交互

1. 多图首屏尽量看见两张有效缩略图，后续图片沿水平方向浏览；在窄卡片中优先保证缩略图可辨认和触控尺寸，再决定显示完整两张还是下一张预览。用真实 390px 双列和 1440px 四列卡片设计，不能拿整屏宽组件代替窄卡片验收。
2. 图片区域高度稳定，不随当前图片横竖比例跳动；卡片缩略图可裁切，点击后的大图仍完整查看。不得拉伸图片。
3. 保留总图片数与明确的继续浏览提示；桌面有可点击的前后入口，手机可自然横滑，键盘用户可访问每个可见预览和翻页动作。单图隐藏无效翻页入口。
4. 优先用原生横向滚动与 CSS scroll snap，不增加轮播库、不自动轮播。选择器只影响本次卡片媒体区。
5. 复用现有预览数量上限；如果未展示全部图片，末端明确显示“查看全部 N 张”，并进入现有详情。不要为了横排一次预载所有原图或视频。
6. 单击第 k 张必须打开同篇第 k 张；滑动结束不能误触打开详情。图片上的重试、收藏、更多菜单也不能冒泡成打开图片。
7. 用户垂直滚动页面仍应自然工作；横滑只由媒体区域承接，不占用整个卡片或页面手势。减少动态效果时去除平滑滚动和装饰动画。

- 不在每次翻页时重绘整张日记；不要使日期、正文、评论预览和菜单状态跟着闪动。

## 4. A：修复草稿生命周期

原因：`saveDraft()` 在内容清空且字段恢复默认时直接 return，既有 localStorage 草稿仍在；`setExpanded(true)` 又会调用 `restoreDraft()`，因此旧内容复活。

最小实现：

1. 用已有账户维度的草稿 key 继续存储；表单恢复为空白默认状态时删除当前账户的旧文字草稿，而非跳过操作。日期默认值与表单初始化共用当前项目的日期规则。
2. 草稿只在确实有草稿、且不会覆盖正在编辑内容时恢复。折叠/展开保留当前输入，不重复用旧快照覆盖，也不反复播报“已恢复”。
3. 明确当前自动保存仅覆盖文字和选项，文件预览不是跨刷新保存的草稿。显示简短提示，例如“文字已暂存本机；刷新后需重新选择本地图片”，不承诺不存在的云草稿能力。
4. 增加清楚的“清空草稿”动作；只有确实会丢弃当前非空内容时复用现有确认能力。普通折叠、展开不弹确认。清理时同步表单、当前账户 key 和媒体预览，并释放 object URL。
5. 本机存储不可写时保留当前输入，并在草稿状态处提示未暂存；不要因 localStorage 抛错打断编辑，也不要显示“已保存”。
6. 成功发布或确认成功加入现有上传队列后再清理相应草稿；失败不能提前清空。账号退出/切换继续遵守现有隔离边界。

验收：复现步骤不再恢复旧标题；正文和非默认分类等真正未发布内容仍可恢复；损坏 JSON、存储写失败、切换账户、发布失败、清空取消均有结果断言。新增针对状态的控制器/纯函数测试，不用只检查源码字符串的测试证明正确。

## 5. B：让手机衣柜筛选完整可用

原因：根目录 `wardrobe.css` 在 820px 以下隐藏第 2、3 个 select；controller 的“可穿”筛选仍工作。当前空态有“换个筛选条件”的文案，却没有手机端可操作的相关条件。

推荐方案：

- 保留搜索和分类主入口。增加一个有文字的“筛选”按钮，展开同页的轻量筛选区域，容纳季节和状态；优先原生 disclosure，不新建独立筛选框架或路由。
- 默认“可穿”可保留，但必须在折叠状态下可见，例如摘要“可穿 · 全部季节”。用户可改为“全部状态 / 待清洗 / 待修补 / 已收起”。
- 显示结果数量和当前非默认条件；“清空筛选”必须具有确定语义。建议提供“查看全部衣物”，一次清除搜索、分类、季节、位置、收藏和状态限制；将状态置为 `all`，不能又恢复到 `available` 导致目标记录继续消失。
- 进入编辑、返回详情、切换视口后，控件、摘要和真实过滤条件保持一致。继续使用当前 controller 的一份状态；不维护第二套仅手机使用的数据。
- 搜索输入补可读名称，不能只依赖 placeholder 和隐藏图标。顶栏“添加衣服”“今天穿什么”、位置管理入口提供可理解的文字；窄屏可换行，不能为了图标化丢失含义。
- 本次范围内的概况和筛选文字回到项目可读字号；输入控件计算字号至少 16px，操作区域至少 44×44px。不要修改无关页面的字体规则。

验收数据至少四种衣服状态、两个季节、两个位置，混合收藏与非收藏。手机真实点击筛选后能找到待清洗衬衫；桌面选季节后缩至手机仍能看见并清除条件；无匹配时能直接查看全部。覆盖 390、768、820/821 和 1440px，以及手机已有大字模式。

## 6. C：菜谱保存只执行一次，失败可恢复

`submit()` 应在第一个异步操作之前进入提交中状态；只禁用按钮不能拦截表单 Enter 或重复事件，必须有控制器级 guard。

1. 添加局部 `isSubmitting`，提前返回重复 submit；保存按钮置 disabled / aria-busy 并显示“保存中…”，完成后在 finally 恢复。状态在表单操作附近可见，且只播报必要变化。
2. 保存前捕获本次输入快照和当前账号。异步期间明确锁定会影响提交的编辑/取消动作，或完整保留后续新输入；推荐本轮采用局部禁用，避免提交结果与屏幕内容不一致。
3. 保留失败时的菜名、食材、步骤、封面选择和编辑 ID。成功完成服务端写入后再重置表单；不得把积分等后续反馈失败报告为“菜谱未保存”并诱导再次提交。
4. 核对 `getCoverForSave()`：当前本地封面失败会被 catch 后返回旧封面，后续仍可能继续保存。用户本次明确选择的封面处理失败时，应停止本次保存并提供重试，不静默换成旧封面或无封面。保留已成功取得的本次上传结果供本次重试使用即可，不建立通用上传事务系统。
5. 结果回来时确认仍是同一账号、同一次编辑操作，不能关闭后来打开的编辑表单或污染新账号界面。沿用现有项目可用的生命周期模式。

最小测试：延迟 repository，连点加 Enter 仍只有一次写入；失败后再试可正常提交；处理封面失败时没有菜谱写入；编辑现有 ID 不变；保存成功但非核心奖励失败不重复写入；账号切换后的迟到回调无 UI 污染。再用浏览器验证按钮忙态、错误可见性、焦点与输入保留。

## 7. D：日记发布表单与状态分组

先完成 A，再做布局。当前表单并非字段越少越好，重点是日常发布所需内容更靠前、附加操作可找到。

推荐结构依次为：媒体选择与预览 → 标题和文字 → 日期/分类/可见范围的简短摘要与“发布选项” → 状态和发布动作。图片链接作为媒体区的次级展开入口，不与主输入永久并排。标题允许空值的现有规则保持不变。

- 日期、分类和当前公开选项即使折叠也必须显示当前摘要；不要用折叠隐藏隐私决策，也不要自行改变 `is_public` 的授权或默认值。文案如需变更，先核对现有权限实际含义。
- 草稿状态与上传状态分开呈现：“文字已暂存本机”不等于“日记已发布”。当前状态放在用户正在操作的表单下方，避免手机滚到底提交时只在上方报错。
- 使用现有上传阶段文本，例如处理第几项、排队、上传中、失败；没有真实总进度就不显示虚构百分比，不增加倒计时或强制停留。
- 弱网加入队列后明确写“已加入上传队列”，提供跳转已有设置上传中心的动作；懒加载后定位真实 `settingsUploads`，不复制第二个上传中心。
- 入队失败保留输入和媒体；入队成功后让表单与提示同步进入明确状态，防止仍显示旧文字让用户误以为没有接收。不得改成自动重复创建新任务。
- 保留拖放、粘贴链接、Live Photo 配对、普通视频、合集数量限制和移动端 VLOG 发布入口。
- 表单内区域自然排布，默认不增加全局 fixed/sticky 发布条；短横屏、软键盘或大字模式下允许滚动，不通过限制视口缩放来弥补布局。

验收：390px 默认空白表单相对本轮约 900px 基准显著缩短，目标至少减少 20%，同时主输入、摘要、发布动作完整可达；1440px 不出现宽而空的上传区。此尺寸目标适用于健康 fixture、标准字号，大字模式以完整可读为准。检查媒体选择后布局、错误定位、断网排队、恢复网络、重复点击与打开上传中心后返回。

## 8. E：空结果和失败状态提供正确动作

只覆盖日记列表、衣柜、心愿；已经正常工作的媒体重试、心愿首次“添加心愿”入口等直接复用，不创建全站空态框架。

| 状态 | 文案要表达什么 | 对应动作 |
| --- | --- | --- |
| 已成功加载，确实没有内容 | 尚未创建 | 打开对应现有创建入口；未登录用户不展示越权动作 |
| 有内容但搜索/筛选未命中 | 哪些条件正在生效 | 清空搜索或明确重置条件，定位回搜索/筛选控件 |
| 正在加载 | 尚未完成查询 | 显示局部 loading/aria-busy，不能短暂宣告“没有内容” |
| 请求失败且没有可用数据 | 读取失败，可以重试 | 重试现有读取路径；进行中禁用重复操作 |
| 有缓存，但刷新失败 | 正在显示上次内容 | 保留列表，局部提示并提供重试，不清空已展示内容 |

具体要求：

1. 日记 `getDiaryGalleryEmptyState()` 不应因非空 search 提前掩盖收藏同步错误或加载状态。先判断当前数据源是否可靠，再判断是否匹配；只对当前选中数据源采用对应状态。
2. 日记空结果提供“清空搜索”，仅清搜索；另需清分类时使用名称明确的动作。保留 VLOG 模式边界，不能无提示退出模式。重置后同步输入、chip、结果和分页可见数量。
3. 衣柜无匹配主动作应为第 5 节的“查看全部衣物”，首次无内容才以“添加衣服”为主。加载失败不能伪装成空衣柜。
4. 心愿同步错误增加重试。优先调用既有 `synchronizeAccountData()`，保留其 single-flight、账号校验和既有错误状态；这是目前账户级同步接口，按钮可标为“重新同步”。不为只取 wishes 绕开它直接写 state，也不借机重写整个账户同步体系。
5. 原有模块持有状态和副作用，视图只渲染并传递明确 action。按钮必须接到真实函数，不能写静态按钮或仅 `location.reload()`。
6. 重绘后恢复到仍存在的控件，不将焦点留在被删除的空态按钮上；aria-live 使用简短结果摘要，不反复宣读整个长列表。

验收：对“空、无匹配、请求中、失败、缓存可用但刷新失败、恢复成功”逐一注入合成状态；验证实际按钮动作、请求次数、数据保留和焦点。列表恢复成功后错误提示消失，失败期间不得重复创建记录或丢失编辑内容。
