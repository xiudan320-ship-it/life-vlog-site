# 手机日记宫格与单／双列选择实施规划

## 1. 目标与授权

用户要求：手机日记照片采用更自然的宫格展示，设置中可以自由选择单列或双列；由 GPT-6 Luna、max 执行代码、验收与部署。

本规划记录需求、验收约束与实际实施结果；完成状态见第 10 节。调研基准为 main `9cb5d97`；开始实施时 HEAD 未变，但工作区已有本规划文件和对应 CHANGELOG 条目，实施中予以保留。后续改动基于该状态完成。

最终体验：单列适合读日记和同时浏览多张照片；双列适合快速浏览更多日记。两种模式均可进入完整相册，不能丢失任何图片。卡片结构统一，整卡高度自然增长，不强行等高。

## 3. 产品规则：设置只提供单列和双列

1. 在“设置 → 外观与使用 → 手机列表布局”提供两个明确选项“单列”“双列”，用现有设计语言的小型分段选择或原生单选组显示当前选择，不再靠点击整行猜测下一状态。
2. 简短说明：“单列看多图，双列看更多日记”。用户可随时切换，不增加第三种布局、宫格开关、裁切开关或复杂配置。
3. 复用现有存储键和账号作用域。已有用户保持其选择；未设置者沿用当前 double 默认值，不批量重置或迁移，不改成强制单列。此偏好是当前设备上的账号偏好，不宣称跨设备同步。
4. 切换立即生效，关闭重开设置、刷新后仍一致。单列／双列互切不丢正文展开状态、点赞／收藏状态、图片顺序或当前阅读位置；以保留当前可见日记作为布局变化时的滚动参考，避免跳回顶端。
5. 在桌面修改偏好只改变之后手机宽度下的选择，桌面仍保持现有四列布局。秘藏自己的单／双列设置独立，不能被改动。
6. 控件有明确可访问名称和选中状态，触控区域至少 44px，键盘操作、设置搜索定位和关闭返回焦点可用。

## 4. 手机单列：自适应宫格

以下规则用于手机布局生效范围内的日记卡片。复用现有实际断点，先核对渲染中的 mobile 判定与 CSS 是否一致，避免另加互相矛盾的断点。

| 图片数 | 展示规则 |
| --- | --- |
| 0 | 不生成图片占位，保留正文及操作；VLOG 等独立媒体按原业务规则处理 |
| 1 | 单张较大预览，沿用合理的比例上下限与完整显示，长图不无限撑高列表 |
| 2 | 两列一行，等尺寸方形单元格 |
| 3 | 三列一行 |
| 4 | 两列两行 |
| 5、6 | 三列两行，五张时最后一格位置自然留空，不复制照片、不做填充假图 |
| 7 及以上 | 三列两行，仅预览前六张，第六格叠加“+N”，N = 总数减六，并提供“查看全部 X 张”的可访问名称 |

宫格间距建议 4–6px，沿用当前圆角和主题表面色。同一篇内的格子大小一致；不同图片数量的日记不必拥有相同图片区高度。

用户之前反馈过缩略图裁切，因此本轮默认保留 `object-fit: contain`，在规整单元格内完整显示原比例照片，空余处使用主题底色。不为追求满格使用拉伸或偷偷恢复 cover；不新增 OCR、智能裁切或图片分类服务。相册中继续完整查看原图、缩放和左右浏览。

普通缩略图点击打开该张图片的原始索引。带 +N 的第六格打开原相册并定位第六张，之后可继续浏览未预览的所有图片，避免第六张失去入口。显示数量与相册总数一致，不能把截断的数组作为完整图片集合传入相册。

多图宫格区域不再横向滚动；手机自然上下滑动时不会误开图片。复用现有点击／拖动保护，删除确实失效的手机轨道专用逻辑，不影响桌面仍在使用的横向轨道。

## 5. 手机双列：封面与张数

每张日记卡片显示第一张媒体作为封面，沿用 contain 和现有合理比例上限，右下角显示“X 张”或等价清晰标识（单张可省略）。双列卡片内部不再塞三列小宫格，也不保留狭窄的横向缩略图轨道。

点击封面从第一张打开完整相册；张数标识可以作为同一按钮的视觉组成，不嵌套按钮。不能下载或自动播放因双列模式不可见的其余预览媒体。

这是本规划的明确设计选择：设置切换的是整份日记列表的列数，同时采用适合卡片宽度的照片展示。不存在另一个需要用户理解的“图片列数”选项。

## 6. 日记框架与保护范围

- 同一种模式内统一作者／日期、正文、媒体、标签和互动的视觉层级及间距；沿用现有卡片结构完成本轮变化，不借机重排全站。
- 卡片宽度受列数控制，整卡高度由内容决定。不设置固定整卡高度，不为无图、无标签的日记保留空区域。
- 保留当前正文展开／收起机制，若现有列表没有长文边界，则局部加入单列约四行、双列约三行的预览与可访问展开入口；避免重复实现已有详情机制。短文不显示无效“展开”。
- 保留桌面四列、桌面现有多图横向浏览、今日心情、评论／回复层级及最近上线的等级样式。保留首页黑猫及全部保护资产。
- 保留单图、视频、Live Photo 的现有入口和标记。隐藏的媒体不能参与自动播放；减少动态效果及低性能设备的原有限制继续有效。
- 加载前预留图片格子空间；失败显示原位置的重试反馈，重试不触发图片打开，成功后不改变对应原始索引。

## 7. 实施顺序与工程约束

1. 先跑通“设置选择 → 持久化 → 画廊模式变化 → 正确打开原相册”的最小闭环，再补宫格数量规则、样式和失败状态。
2. 使用现有模块、偏好服务、图片查看器和原生 CSS Grid；不引入轮播／拼图库，不增加后端接口和数据库字段。新业务不放进 app.js。
3. 渲染视图与布局偏好由各自模块负责。需要数量布局规则时使用简单纯函数，不建立通用排版引擎。避免为三个展示模式重复生成三套隐藏媒体 DOM。
4. 追踪 applyMobileFeedLayout 目前仅切换类并调度布局的事实：如果新方案需要更换媒体 DOM，补上真实的重渲染或最小视图更新通路，确保不刷新也生效，窗口越过断点后亦正确。
5. 本轮方案已确定，可作为现有卡片与设置的局部修改直接实现。若确需进入 Figma 比较方案，按 docs/FIGMA_WORKFLOW.md 及对应技能操作，复用已有项目；工具限额时记录限制，继续代码与浏览器验收，不等待配额、不虚报设计节点。
6. 删除被替代且无其他使用方的手机轨道实现。桌面仍使用的轨道属于保留需求，不作为过时兼容层删除。

## 8. 验收与测试

只使用确定性内存 fixture，不登录真实账户、不读取真实日记做自动化验收。

| 验收组 | 必须证明的行为 |
| --- | --- |
| 图片数量 | 0、1、2、3、4、5、6、7、10 张；单列列数／行数、预览上限、+N 正确，双列只有封面但相册全部可达 |
| 媒体类型 | 横图、竖图、极长图、缺少尺寸、视频／Live Photo；不变形、不溢出、加载失败可重试 |
| 索引 | 点击第三格打开第三张，第六格打开第六张并可向后翻，双列从第一张打开；不是仅检查 DOM 中有索引属性 |
| 设置生命周期 | 真实点击两种选项立即生效，重开／刷新保持，账号 A/B/访客偏好不串；单列↔双列及手机↔桌面转换正确 |
| 卡片与交互 | 长短文、展开、收藏、评论、更多菜单正常；滚动不误开图，重排不跳回列表顶部，弹窗关闭焦点合理 |
| 视觉 | 手机 375/390/430，两种列数；768/1024/1440 验证断点与桌面保护，至少一个手机宽度补横屏和大字号；深浅主题、键盘、reduced-motion |
| 性能 | 不生成重复的隐藏图片列表，双列隐藏图不额外加载／播放，懒加载保留；构建预算不因任务任意提高 |

更新 tests/diary-gallery-view.mjs 中被新需求替代的手机 rail 断言；保留桌面 rail 的相关回归。浏览器测试必须使用真实渲染的 fixture 日记，不仅临时注入一个手写宫格来证明样式存在。图片打开、偏好持久化和媒体失败恢复需要实际操作与结果断言。

按改动运行相关模块、静态／结构检查及 build、build budget；使用新构建执行受影响浏览器回归与 Axe。发布时统一清单要求的完整门禁仍需通过，不通过时定位修复，不能降低门禁。已通过的检查只在新改动或未决问题要求时重跑。

用户已明确授权本任务实现及部署。直接在 main 完成，保留其他任务修改，不新建分支／工作树，不混入无关工作。先同步此规划的实际完成表、必要的设置／日记设计规范及 CHANGELOG，模块职责真正变化才更新 MODULE_MAP。
